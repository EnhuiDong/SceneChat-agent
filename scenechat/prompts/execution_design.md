# 执行设计：完成什么，由谁亲自决定，怎样成为真实结果

先在内部核对一张小型因果表，再输出既有 world JSON，不输出额外设计字段：用户需要的完成事项 → 有权独立选择的人 → 专用动作 → 实际登记的状态 → 结束条件 → 本动作不能代替的他人选择或后续结果。这张表只设计机制，不安排人物未来台词、情绪、妥协与成功。

使用已有实体、固定状态键、能力效果、阶段与组合结束条件；不得新增条件表达式或脚本。description 不执行前提。只有完成事项相关的关键对象才需建模，不把所有生活用品变成待办。

关键行动依赖已完成结果时，使用规则 requires 的类型化前提：world_equals、entity_equals、agent_location 或 all_active_at_location。数组中所有项须在本次效果执行前成立。发车要求伤员载入且全员实际上车，就分别声明载入状态和全员所在地点；仅写进 description/能力说明不算约束。条件失败不选低优先级的无条件成功规则来绕过。前提不是结束条件，也不安排人物未来意愿；普通交流通常留空。不支持脚本、嵌套条件或比较表达式。

## 多人独立确认

“双方签收”不是任意一人调用 complete 就完成双方。可声明 object 实体 receipt，state={"sender_signed":false,"receiver_signed":false}。公共 sign 规则 action_type=sign、effect_mode=ability、effects=[]，匹配双方执行标签；人物生成时各自拥有 sign 能力，只更新自己那一个固定键。终止用 all_of，分别 entity_equals(receipt,sender_signed,true) 与 entity_equals(receipt,receiver_signed,true)。每项条件有独立 id，角色名称、执行标签、能力 ID 由本场实际设定决定，不照抄示例。

不得在公共 sign 规则里同时写两人的 true，也不复制对方的能力效果。普通说话、邀请签字和点头不自动签收。不要用可重复的 increment_world=1 冒充不同人均已签字；同一人重复不能代替另一人。如果用户允许代签或授权，则按其明确规则建立相应权限，不能默认添加。

人物还未生成时，world 的规则说明中明确此动作需“每位持有者能力仅更新自己的固定键”，并声明所有结束依赖键；角色阶段必须提供这些能力。不要把完成键写成不存在的 $actor_signed 或动态 key。effect_mode=ability 的公共 effects 不执行，不能依赖它们证明完成可达。

不同人的离开、签收或决定若使用相同 action_type 和 target_scope，公共规则不能各写一个人的固定完成键再靠 priority 区分：高优先级会遮挡另一人的规则，前提失败也不会回退。使用不重叠的 allowed_roles 执行标签并在人物档案落实，或使用上述各自能力方案。self 只限定动作目标，不会自动将固定 entity 键绑定到本人。本人离开还应登记真实位置或 active 状态，不能只改物品上的 left=true 却继续把离开的人留在原场景发言。

## 合作行动

本人登车使用 move_agent(target=$actor,value=实际地点)。搬运另一人必须明确有权搬运的规则，不默认所有人替同伴移动。全体上车可以用 all_active_at_location；若用户真正要求车辆出发或安全抵达，那是另一项实际结果，需要独立效果来源和相应阶段，不能在“上车”的结束描述里顺便宣告。

需要全体实际行动之后才能推进的 all_eligible_acted 阶段，填写 completion_action_types 为对应的获准实际动作类型，例如 board。speak/pass 可以保留供交流，但不计入该阶段的真实参与。每位 actor_roles 覆盖的人必须有合法执行路径；单人职责只覆盖实际执行者，不让所有人重复代办。普通发言阶段留空，manual、投票或环境阶段不使用此字段。它只选择哪些已有动作计数，不引入条件脚本，也不能代替具体结果的结束条件。

已声明关键道具的归属、收好、损坏等可变状态，必须有对应效果；背景描述只说明开场，演员以较新的执行状态为准。若用户只要求当场尝试，不偷换成已修好；若要求结果，机制不能只有永久“正在尝试”。复杂机制无法表达时保留明确限制，不让旁白偷偷结算。

## 交流及规则场景

结束一次谈话表示当前交流停止，不等于所有人和解、信念转变或终身目标达成。仅确需参与者独立决定时记录各自选择，不给平常告别强加双方签字。公开结束动作与普通 speak/act 分开，不每次说话都结束。

规则题材的一轮发言、选票登记、结算、淘汰与胜负各有真实依据。有限阶段用既有推进方式，manual 有合法出口；特殊动作列入 allowed_action_types。计票不依赖旁白，阵营名称和胜负含义一致。不为丰富设定增加另一套无条件胜负按钮。

## 最后交叉核对

关键主线不是反复“讨论、理解、确认”的清单：每一项关键障碍要有此时可获得的信息、可亲自作出的选择或可执行的尝试，给出已做之后局面有什么不同。允许拒绝、保留分歧和不同结果，不安排所有人必须妥协或轮流重复核验。不将抽象文风、表达差异、紧张气氛或连续追问作为后续行动必须通过的节点前提。

普通物品的分配、整理若声明成会变化的 entity.state，必须提供相应的真实执行来源；不会参与条件/结算且不需要精确追踪的开场细节留在文本背景。不能声明永久 owner=undecided/sorted=false，却让人物仅靠无效果的普通 act 来完成后又每轮读到未完成。只有关键变化需要专用接口，不给每杯水、每次擦桌子增加状态工作单。

public_rules_markdown、effect、状态类型、人物权限、阶段许可、termination_rules 描述的是同一件事。检查每个 all_of 子条件都能通过实际可执行来源改变；检查某个行动不会一次代替多个人独立选择；检查结束文案不宣告比条件更多的结果。保留用户明确规则，不自行降低完成标准。

节点 completion_conditions 与结束/行动前提的条件词表不同：节点仅支持 world_equals、entity_equals、agent_location、goal_equals。全体到达节点可用每个人各一项 agent_location，不能照抄结束条件的 all_active_at_location。改为 narrative 时 completion_conditions 必须为空数组；不能只改模式留下无效条件，也不能为了修复节点删除护卫/维修/过桥的真实前提。
